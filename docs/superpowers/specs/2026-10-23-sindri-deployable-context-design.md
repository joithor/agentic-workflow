## 0. The short version

### For you

One pod runs Sindri, Onyx (the search over chat and tickets) and your coding agents together, installed from one chart. The agents
reach Sindri on the pod's own loopback, the same way an agent on your laptop does today. They can ask it about the code and docs of the
repos you approve, the chat and tickets the map already links, and your work queue, and they can file work requests that wait for you
to decide. Nothing is opened to the cluster: there is no Service, nothing listens on the pod's address, and nobody outside the pod
reads anything. Your own rights stay yours: you reach the pod through `kubectl port-forward` and `kubectl exec`, and the agents have
no way into Sindri's data or a terminal in its container.
Setting it up is a handful of commands, each one step, in two terminals (`connect` holds the first). The agents and the repos they
will work on are in the chart's values. In order:

1. Create each agent's own Secret (its model login and its git read credential) and the git-token Secrets, then install the chart.
2. Terminal 1: `scripts/sindri-pod.sh connect` (opens the app on the pod).
3. Terminal 2: `scripts/sindri-pod.sh doctor`, until Onyx shows ready.
4. Terminal 1: `scripts/sindri-pod.sh connect --onyx` (the one Onyx sign-up).
5. Terminal 2: `scripts/sindri-pod.sh profile edit --no-approve` (allow your git host), `scripts/sindri-pod.sh repo add <name> <url>` for
   each repo, and `scripts/sindri-pod.sh approve` once.

The agents' config already lists each repo, because the chart wrote it. The exact commands, with every flag, are in §C.3. Your answers are
in the box in §1: only the agents in the pod use Sindri, the pod runs your agents on one bigger node (the layout and what it costs are in
the box), and the agents don't search chat and tickets themselves. If you only have a small node, Onyx stays off and the agents get code and docs only.

### For builders

Today Sindri is a desktop program: it binds to loopback only, trusts whoever holds the token file in its home, runs one copy per
person, and manages Onyx with Docker Compose on the same machine. In a pod, most of that stays. This spec turns it into:

1. **One image** (`Dockerfile` at the repo root, built by CI from the repo): Sindri's control plane (as `sindri-app` publishes it),
   the pinned `temporal` binary, the code-index tools, `git`, and nothing secret. It runs `sindri serve` in the foreground with all
   state on one volume. It has no Docker CLI and no daemon.
2. **Onyx beside it, in the same pod, from one chart.** Onyx's own prepackaged images run next to Sindri as ordinary containers.
   Nothing is privileged and nothing runs Docker. A script renders them from Onyx's pinned Compose file, so an Onyx upgrade is:
   bump the lock, re-render, `helm upgrade`. Sindri uses this Onyx as one it does not manage; one command, `sindri onyx attach`,
   does the account steps.
3. **No new door.** Sindri's API stays a loopback-only listener, byte for byte; there is no Service and nothing listens on the pod's
   address. The owner, through `kubectl port-forward`, keeps every right they have today.
4. **The agents are containers of the same pod** (`agents[]` in the chart). They are ordinary local sessions on the pod's loopback: the same 13 `/sindri/mcp` tools a laptop session gets (the six `context_*` reads with `context_map_whole`, the six read-only `sindri_*` tools about the work queue, and `sindri_request`), and they see what a laptop session sees: the code and docs of the approved repos and the chat and tickets already linked into the map, never Onyx itself (the owner's rule of 2026-10-15). They bring their own image, login and git clone; they never mount Sindri's data volume (§B.2, §C.1).
5. **Always fresh**: a new Sindri service pulls each repo's default branch; the code index, the docs index and the map follow it
   as they already do; Onyx's connectors (set up once by the owner in Onyx's page) keep tickets and chat current; Sindri's existing
   sync and refresh services read them and link what they find into the map.
6. **The owner's steps** stay one command or one click each: `scripts/sindri-pod.sh connect` opens the app on the pod;
   `connect --onyx` also forwards Onyx's page for the one browser sign-up and runs `sindri onyx attach` in the pod, before the one
   approval; `profile edit` is the one way to change a profile key in the pod; approvals are the app's existing
   one-click-and-type confirmations (or `scripts/sindri-pod.sh approve` at a terminal).
7. **No model in Sindri v1.** Everything the map and the six `context_*` tools do works without one; only labelling suggested links and the
   decisions pass need a model, and they stay off in the pod (K12). The agents have their own models and logins.

The price of one unit: the pod holds all of Onyx, Sindri, the Ollama sidecar and the agents, so it must fit **one node**. Onyx's floor
alone is about 5.5 GiB of memory and its images are about 11 GB to pull, and every agent adds its own CPU, memory and disk; the node
floor is computed from the chart's values (C.1, with the numbers for 5 and 8 agents). The spike measures the whole pod (K-S0). A node too small for Onyx means Onyx off.

## 2. Part A: the image and the pod

### A.1 The Dockerfile

At the repo root, multi-stage, every `FROM` by digest (from `deploy/images.lock`):

1. **build** (`mcr.microsoft.com/dotnet/sdk:10.0.401-noble@sha256:…`, the SDK `global.json` pins): restore with the locked
   restore, `dotnet publish src/Sindri/Aw.Sindri.Host -c Release --no-self-contained -p:AwRecipesDir=<recipes/sindri>`, the same
   flags `scripts/sindri-app.sh` uses; `judge` and `aw-packets` NativeAOT for the target platform (`AW_SINDRI_JUDGE`,
   `AW_PACKETS_BIN` point at them); the shipped recipes' evals run (`recipe eval --shipped`) and fail the build as they fail
   `sindri-app`. `sindri-ui` is not built: the image has no desktop.
2. **tools**: `temporal` from `binaries.lock` (download, sha256 check, as `scripts/binaries-lock.sh fetch temporal` does), and
   graphify at the code index's pin in a venv (`uv`, as `scripts/install-deps.sh` does).
3. **runtime** (`mcr.microsoft.com/dotnet/aspnet:10.0-noble@sha256:…`): `git`, `bubblewrap`, `tini` as PID 1 (it reaps the
   detached Temporal process), `procps` (Sindri's `DevServerProcesses` runs `ps` and `kill` for the Temporal dev server on Linux
   too), `curl` (the exec probes of C.1), the three stages' outputs under `/opt/sindri`, a fixed non-root user, `ENTRYPOINT ["tini","--","/opt/sindri/start.sh"]`,
   where `start.sh` copies the temporal binary to where Sindri looks for it
   (`$AW_STATE_DIR/cache/bin/temporal-<ver>/temporal`, with no override) whenever that versioned directory is missing (a new
   volume, or a new temporal pin after an upgrade) and then `exec`s `/opt/sindri/sindri serve`. Every variable a `kubectl exec`
   needs is image `ENV`, not set by `start.sh` (an exec doesn't run it): `AW_STATE_DIR=/data/state`,
   `AW_SINDRI_HOME=/data/state/sindri-app`, `HOME=/data/home`, `AW_SINDRI_DEPLOY=pod`; the chart adds the rest. Read-only root
   filesystem; `/data` and `/tmp` writable; the git and `uv` and graphify caches live under `/data` (a read-only root has no other
   writable home). `/opt/sindri` is world-readable. The image has no Docker CLI, no Compose plugin and no daemon.

`serve` runs in the foreground, ignores SIGHUP and stops cleanly on SIGTERM (it already does: `ServeCommand.cs`), stopping its
Temporal dev server within 10 s. `serve`'s Onyx hooks (`OnyxServeHooks`) act only on a Sindri-**managed** Onyx and "an unmanaged
Onyx is never touched", so in the pod, where Onyx is unmanaged (§B.3), a Sindri restart leaves Onyx's containers running: no code
change. When the whole pod stops, Onyx's containers stop with it, at the same time (all are ordinary containers, so every container gets the stop signal at once, the agents included: an agent's running processes stop on every rollout, while its files stay on its workspace claim; C.1 says what survives). The pod's
grace period is 120 s: Sindri's own stop is at most about 30 s (20 s for launched sessions, 10 s for Temporal); Postgres and
OpenSearch get the rest to flush; K-S0 times a pod delete with Postgres under write load.

| Start order | **No Onyx container is a native sidecar, and none gates Sindri.** All containers, Sindri's and Onyx's, are ordinary containers that start together; the only init container is the one that prepares the volume directories (Volumes row). **Sindri's container is first in the pod spec, and that init container runs Sindri's own image**: the kubelet pulls and starts in spec order, so Sindri starts as soon as its image is there, while the Onyx images are still pulling (an init container on another image would add a pull in front of everything). K-S0 and the kind run measure **time-to-Sindri-up on a cold node** (`/sindri/ping` answering before the last Onyx image finishes pulling) and record it. Compose's `depends_on` is not turned into pod ordering: Onyx's own images retry (`api_server` runs `alembic upgrade head` first and restarts under Kubernetes' restart policy if the database is late; nginx's start script waits for the API server; the model servers are `service_started`, not `service_healthy`, in Compose), and **K-S0 verifies** that the pod settles with no ordering at all. Why: Sindri must be up in seconds even while ~11 GB of images are still pulling or OpenSearch is crash-looping, so the owner can run `doctor`, approve a profile and the agents can serve code and docs. **Probes:** Onyx containers get **liveness probes only** (generous, from their Compose health checks where Compose has one, with long start periods; Compose has **no health check for OpenSearch**, so its liveness probe is one we write: a TCP check on `9200`, because the port answers HTTPS with a demo certificate) and **no readiness probes**; Sindri's readiness is an exec probe of `/sindri/ping` on the loopback (C.1). There is no Service and nothing routes by the pod's Ready condition, so a crash-looping Onyx container (which makes the pod not Ready) does not stop Sindri from answering the agents, and the answer carries Onyx's degraded note (`SND-CONTEXT-010`). Sindri's readiness probe decides only the pod's Ready condition (what `helm --wait` and `kubectl rollout status` read). **The StatefulSet sets `podManagementPolicy: Parallel`.** With the default `OrderedReady` the controller does not roll a corrected template over a pod that is not Ready (its reconcile stops before the update step; Kubernetes' StatefulSet documentation calls this the forced rollback), and a looping Onyx container is exactly such a pod, so the `helm upgrade` that fixes it (raise a limit, fix an env var) would never apply. With one replica `Parallel` costs nothing (it changes only how several pods are created and deleted) and the update step replaces an outdated pod without waiting for it to be Ready. The chart test asserts the field, and the kind run breaks an Onyx env var, runs `helm upgrade` with the fix and expects the pod to roll with no manual delete. If a cluster's controller still waits, the fallback is `helm upgrade` and then `kubectl delete pod <pod>` (a normal delete, never forced, A2b). Install and upgrade both run `--timeout 30m` and without `--wait`. The pod-state table (C.1) says what each state means |
| Volumes | Onyx's named volumes become **one claim** (`onyx-data`, default 60 Gi) with a `subPath` for each that must persist: `db_volume` (Postgres; PGDATA is a subdirectory so the filesystem's `lost+found` doesn't break `initdb`) and `opensearch-data`. **The model caches get no volume over the image's baked path.** Docker seeds a new named volume from the image; a Kubernetes volume at that path would hide whatever the image baked in and force a download at start. K-S0 lists where each model server's weights live and whether they download at start: if baked in, the path stays as the image has it (a writable `emptyDir` only if the process writes there); if they download, a volume is allowed and the weights are pinned (Egress row). Postgres gets a memory-backed `emptyDir` at `/dev/shm` (1 Gi, from Compose's `shm_size: 1g`, counted in its memory limit). The log volumes become `emptyDir`s with a `sizeLimit` of 512 Mi (logs also go to stdout); `minio_data` and `file-system` aren't used; Redis keeps its Compose `tmpfs`. **subPath directories** the kubelet creates are often root-owned and outside `fsGroup`, so one plain, unprivileged init container (Sindri's image, which has a shell, `mkdir` and `chown`) creates each directory and sets its owner to the uid that container runs as (adding `CHOWN` and `FOWNER` only if K-S0 shows the claim's filesystem needs them; K-S0 verifies each directory). The pod sets `fsGroup` and `fsGroupChangePolicy: OnRootMismatch`. nginx's `../data/nginx` bind mount is a ConfigMap rendered from the committed copies of the files whose sha256 `onyx.lock` pins. The claim is part of the backup procedure (K7) |
| Secrets | A Secret the chart creates on first install (random values, kept across `helm upgrade` by a `lookup`) holds `POSTGRES_PASSWORD`, `OPENSEARCH_ADMIN_PASSWORD` (which the Compose file passes to OpenSearch as `OPENSEARCH_INITIAL_ADMIN_PASSWORD`), `USER_AUTH_SECRET` and `ENCRYPTION_KEY_SECRET`, each by name (the last two have no Compose default, so `--check`'s required-keys list covers them, Rendering row), and is mounted into Onyx's containers only, never into Sindri's or Ollama's. Because all the containers share the pod's loopback these are not a boundary against another container of the pod (§6); they stop the well-known Compose defaults from being the real passwords. **The Secret carries `helm.sh/resource-policy: keep`**, so `helm uninstall` leaves it beside the claims, and a reinstall with the same release name and namespace finds it by `lookup` (Helm adopts it; the values stay in step with the data on the kept claims). **`onyx.existingSecret`** names a Secret the owner made with the same keys: the chart then makes none and skips `lookup`; it is **required when the chart is rendered with `helm template` and applied** (Argo CD, Flux and the like), whose renderer sees `lookup` empty and would re-randomize the values on every sync. **A reinstall without the Secret** (deleted by hand, or the namespace was) generates new values: Postgres rejects the new password (the old one is in its data directory) and every stored connector credential is undecryptable (the encryption key changed), so Onyx does not come up usable; the fix is to restore the exported Secret (K7), or, if it is lost, to start Onyx over from an empty claim (deploy.md, which warns it deletes everything Onyx holds). `lookup` returns nothing under `helm template` and `--dry-run`, so the CI render test sees fresh random values on every run: it compares the Secret's **keys**, not values, and the heavy kind test proves the values survive a `helm upgrade` and an uninstall followed by a reinstall on the kept claims (Onyx still starts) |
| Resources | Every container sets requests **equal to** limits, so the pod is **Guaranteed QoS** and node pressure doesn't pick it first (an eviction would take Sindri down with Onyx). The numbers for Sindri and Ollama come from K-A1's `docker run` (K-C1 ships with them), Onyx's from K-S0's measurement (K-O1 adds them), and they become the minimums in `values.schema.json`, not prose. The sum of the memory limits is at least K-S0's re-measured figure for the sizing set (the lock's `docker-memory-bytes`, 5.5 GiB, is for the stock set), with OpenSearch's limit at least twice its heap. **The pod's footprint is all of Onyx plus Sindri plus Ollama plus the agents, and must fit one node: the node floor of C.1, computed from the agents in the values (the base alone needs 8 vCPU, 28 GiB and 75 GiB of node disk, plus 110 GiB of volumes; one default agent makes it 12, 36 and 95, plus 150), the owner's choice of 2026-10-23.** The starting requests and limits (C.1), `ephemeral-storage` ones included (C.1 Storage has Onyx's per-container numbers, 12 Gi together), are sized for it and are the minimums in `values.schema.json`; the kind run and K-S0 record the measured CPU, memory and disk, which may lower the numbers in a later chart revision but do not gate the node choice |
| Egress | The kubelet pulls Onyx's images (about 11 GB across the pod; the registries `onyx.lock` names), so the pod's first start takes minutes. At run time the pod needs the git hosts, Onyx's connectors' services (the chat and ticket systems the owner connects), and, if the model servers fetch their weights at start (K-S0 records it, Volumes row), the model hub's host. **Weights are pinned:** the Hugging Face revision of each model is set by an environment setting K-S0 names, and Ollama's model is pulled by digest; each is verified before Sindri serves queries (doctor shows the result). The kind run records every host the pod contacts at start and deploy.md allowlists exactly those. Onyx's web connector can fetch cluster-internal addresses too, **and the pod's own loopback** (§6), so the connector checklist says to give it only public URLs |
| Not run in the pod | `onyx up`, `onyx down`, `docker`, `docker compose`: Sindri's managed mode (preflight, fetch, render, `OnyxServeHooks`) is for a laptop, and an unmanaged Onyx is never touched by `serve` (§A.1) |

## 3. Part B: the network (nothing changes; the agents are local callers)

Today (API spec §6): loopback only, `LoopbackGuard` (it checks the **Host** header and any browser **Origin**, not the connection's
address), one human token file per serve start, no other auth, and a request with no caller headers is a tokenless `session`.
Pod mode opens nothing: the listener stays loopback-only. The agents are containers of the pod, which shares one loopback (§6), so
they are callers like the sessions on a laptop. Revision 4's cluster door (an any-address listener, a Service, a `shared` caller)
was removed by the owner's answer q80 (§12).

### B.1 The owner's rights: unchanged

- The API listener's behaviour and its guard rules stay exactly as they are. `kubectl port-forward`
  reaches the pod's loopback (the container runtime connects from inside the pod's network namespace), so the owner arrives as
  loopback with `Host: localhost`, which the guard allows. `kubectl exec -it` gives the CLI a terminal and none of the agent
  signals, so it calls as the human at a terminal and the protected verbs (`profile approve`, `recipe approve-all`, `onyx attach`)
  work as they do on a laptop; without `-t` it calls as a session and is refused (`SND-AUTH-002`), as it should be.
- The desktop app reaches it through `scripts/sindri-pod.sh connect` (Part C.3).

### B.2 The agents in the pod: local callers

There is no second listener, no new route, no new client kind and no change to `McpToolTable`'s rows. "Local caller" means any
process that reaches the API on the pod's loopback: the owner's forward and `exec`, Sindri's own CLI, the agents, and the other
containers (§6). It is a place, not a grant: a local caller is a **session** unless it presents the human token. (Earlier drafts
called loopback "the owner's rights"; the owner's rights need the token as well.)

| Aspect | Rule |
|---|---|
| Listener | Unchanged in pod mode. `ServePort.Listen` (`ServePort.cs:35`) and `LoopbackBinding.Build` (`LoopbackBinding.cs:40`) listen on `IPAddress.Loopback` only: no any-address listener, no pod-mode exception, no `Service`. A unit test fails the build if any `Listen` in `src/Sindri` is not loopback, pod mode included. `control.json` records the loopback URL, and `connect` forwards that port to the pod |

| Repo binding (the MCP config) | Each agent container gets one MCP config file, in exactly the document `McpLaunchConfig.Render` (`src/Sindri/Aw.Sindri.Infrastructure/Launch/McpLaunchConfig.cs`) writes for a launched Claude Code session: `{"mcpServers":{"<name>":{"type":"http","url":"http://127.0.0.1:<port>/sindri/mcp","headers":{"X-Sindri-Repo":"<repo>"}}}}`, with one entry per repo (Render writes one entry named `sindri`; the chart names each entry itself by a fixed mapping, `sindri-` plus the repo name with every character outside `[a-z0-9_-]` turned into `-` (repo names may have a `.`), so several coexist, and `values.schema.json` rejects two `mcpRepos` of one agent that map to the same name, `a.b` and `a-b` for example), the port from `sindri.port` (`AW_SINDRI_PORT`). Without `"type":"http"` and the `mcpServers` wrapper Claude Code will not load it. **The chart writes it:** `agents[].mcpRepos` lists the repo names (the names `repo add` takes), and the chart renders a ConfigMap mounted read-only into that agent container only, at `/etc/agent/mcp.json` (`agents[].mcpConfig.path`), **outside any clone and outside the workspace**: a mount inside the clone would make `git clone` refuse a non-empty directory or leave an untracked file. For an agent whose `mcpConfig.format` is `claude` (the default, and the only format in v1) the chart puts the single token `--mcp-config=/etc/agent/mcp.json` (with `=`, never as two words) at the front of its `args`, before the deployer's own args, because Claude Code's `--mcp-config` takes a list and would swallow a following prompt or subcommand word as a second config path (C.1 Permission); the launcher passes a file by flag and not by project discovery; another CLI's format and flag are values added when needed. The profile is not a chart value, so the list is the deployer's and must match the approved profile: a name the profile lacks is refused with the codes above (003, 045 or `SND-CLI-003`, by tool), and doctor compares the two (A2c). `repo add` prints "add <name> to agents[].mcpRepos and run helm upgrade, which restarts the whole pod (Sindri, Onyx and every agent)". | Chat and tickets | The 2026-10-15 rule stands: `ScopeRules.MayRead` denies every `Intent` source (Onyx) to a session, so an agent's call never queries Onyx; it sees only the records and decisions already linked into the map. | Limits | None new: the tools' own budgets, the open-request cap (`SND-REQ-002`) and today's session rules apply, as on a laptop. ### B.3 Onyx on the pod's loopback: unmanaged, attached

Nothing changes in the query adapter. Onyx's `nginx` answers on `http://127.0.0.1:<onyx.port>` (§A.3), so `OnyxSettings.CheckUrl`'s
loopback rule (`localhost`, `127.*`, `[::1]`) passes as it is. The profile's section is the unmanaged shape, `context.sources.onyx`
with `url: http://127.0.0.1:<onyx.port>`, `token: <secret pointer>`, `version: v4.9.0` and `managed: false` (a managed one must be
exactly `http://127.0.0.1:<port>` and is started by `serve`; an unmanaged one is never touched, `OnyxServeHooks`). The pod needs
**the account stage only**, so the verb is small:

- `sindri onyx attach [--url http://127.0.0.1:<port>] [--adopt]` (default URL from `AW_SINDRI_ONYX_URL`, which the chart sets). A **protected
  verb** like `onyx up`: a human at a terminal only (an agent session or a non-terminal gets `SND-AUTH-002`, exit 1). It first **waits for
  Onyx's health route** (up to 20 minutes; `--no-wait` checks once), because right after install Onyx's images are still pulling or `api_server` is
  migrating: every 30 s it prints "Onyx is still starting: images pulling or the database migrating (<containers not answering>), <m> min"
  (the containers named from `AW_SINDRI_ONYX_PORTS`), and Ctrl-C and running it again later is safe. After 20 minutes it ends with `SND-ONYX-016`,
  exit 1: "Onyx did not answer within 20 minutes (<container> still not answering). It may still be pulling images or migrating its database.
  Run `sindri-pod.sh doctor` to see which container is not answering, then run `sindri-pod.sh connect --onyx` again; waiting again is safe." It then checks
  the release `context/onyx.lock` pins and runs the same account stage as `onyx up`
  (the owner's sign-up in the browser, Sindri's dedicated user and token, the profile section above). It **proposes** that section
  and never approves it: the install order (§C.3) runs `attach` before the one `profile approve`, so the Onyx source, the repos and
  the switches are approved once. It starts, pulls and writes nothing in Onyx's workspace, and is safe to re-run.
- **The first sign-up is Onyx's admin.** Between the pod starting and `attach`, any container of the pod could register first.
  `attach` therefore refuses with `SND-ONYX-014` when Onyx already holds an account that this setup did not create: it counts
  Onyx's users before the sign-up step; zero is fine, and one is fine only if it is the account `attach` recorded on Sindri's
  volume (`onyx-attach.json`, owner-only) at an earlier, dropped run. **Until `connect --onyx` has run, Onyx's first
  account is unclaimed:** the chart's NOTES say so and print `connect --onyx` as the step to take once `sindri-pod.sh doctor` shows Onyx ready, so do it soon after install. Closing sign-up after the first account is a **required K-S0 result** (§7 item 6) that the chart sets: without it an agent could register a second account and read Onyx directly, which would defeat the owner's rule that agents never query Onyx (q82). If Onyx cannot close it, §6 and the NOTES name the exposure plainly.
- **`attach --adopt`: an Onyx whose account an earlier Sindri volume made** (the volume was lost, or restored from an older
  snapshot than Onyx's, which is a normal mishap). `SND-ONYX-014` is not a reason to wipe anything. On the owner's machine the command is `sindri-pod.sh connect --onyx --adopt`, which passes `--adopt` to `attach`. With `--adopt`, at a terminal,
  the owner is asked for the existing admin's email and password (not shown, never stored, in no log, file or argument, as
  `onyx up` asks for them), `attach` logs in with them, checks the account is an admin, and then runs the same steps as a first
  attach to make Sindri's own user and a **fresh token**; it records the account in `onyx-attach.json`. It never deletes or
  changes anything else in Onyx. If the owner did not make that account, they must not adopt it: the only fix is an empty Onyx
  claim, which deletes everything Onyx holds (its data, its connectors and their OAuth credentials), and the fix text says so (deploy.md has the steps, §C.5).
- **Already attached** means all three hold: the recorded token still resolves and Onyx takes it as an admin, Onyx answers its
  health route, and `/api/version` equals the release `context/onyx.lock` pins. Then `attach` says so ("Onyx is already attached
  (release v4.9.0). Nothing to do.") and exits 0, without waiting for Enter. After an Onyx upgrade (§C.5) the version differs, so it
  is **not** a no-op: it says "Updating the pinned version to v4.9.x", rewrites the profile section's `version` and proposes it for
  the next approval.
- **How it ends.** Every run ends with a last line and the next step. Attached: "Onyx is attached. Next: allow your git host with
  `sindri-pod.sh profile edit --no-approve`, add repos with `sindri-pod.sh repo add <name> <url>`, then `sindri-pod.sh approve` once." Exit codes: 0 attached or already
  attached; 1 refused or failed, with the code printed (`SND-AUTH-002`, `SND-ONYX-014`, …); 2 usage or a tool error.
- **Onyx off.** With `AW_SINDRI_ONYX_ENABLED=false` `attach` refuses with `SND-ONYX-015` ("This install runs without Onyx
  (onyx.enabled=false). Set it to true and run helm upgrade to add Onyx."), and the approve preview says business context is
  unavailable (§C.3).
- **The address printed at sign-up** is the owner's forwarded one: `connect --onyx` passes it in `AW_SINDRI_ONYX_FORWARD_URL`
  through the exec; with that unset (a plain `kubectl exec`) `attach` prints the in-pod address and says to port-forward it.
- It revives from the branch `feat/sindri-onyx-attach` (`cb225bf00`, a wip) **by cherry-picking `cb225bf00` alone onto a fresh branch
  off main, not by a rebase**: the branch stacks `87028b190` (the `network: cluster` setting, `OnyxClusterPolicy` and
  `AW_SINDRI_ONYX_HOSTS`) and K-A1's two commits (`a1c21244e`, `a1ff34780`) under it, and `cb225bf00` itself also edits cluster-name code
  (`OnyxAttachClusterNameTests`, `OnyxOrigin`, the `HttpOnyx*` adapters, `YamlOnyxProfileWriter` and its tests), so the builder keeps
  the service, the `IOnyxAccountStage` split of the account steps, the verb and its catalog row, and leaves those pieces out; the wip's
  refusal of a loopback address is reversed (attach is for the loopback Onyx here), and no network setting is read. It needs
  nothing from K-S0 or K-A1.
- If Onyx is unreachable, `context_query` answers with its code and docs hits and a note that Onyx is unavailable (the existing
  partial-answer behaviour), doctor goes warn, and nothing else stops.

## 4. Part C: running it (context lane)

### C.1 The chart

`deploy/helm/sindri/` (new, ours), one release: a StatefulSet of one (`podManagementPolicy: Parallel`, A.3 Start order) whose pod holds Sindri, the Ollama sidecar (pinned to
`OLLAMA_HOST=127.0.0.1:11434` so it never listens on the pod's address), **Onyx's containers (§A.3, rendered by
`scripts/onyx-pod.mjs` into one template file, never edited by hand)** and **the agents (below), one container each**; the volume claims (`/data`, default 50 Gi; `onyx-data`,
default 60 Gi; and one standalone, kept workspace claim per agent, default 40 Gi); the images by digest; the env from a Secret (`env:` pointers) and Onyx's own Secret (§A.3). **There is no Service:** nothing in the pod listens on
the pod's address (§6), so there is nothing to publish; the owner's `connect` forwards the API port, and Onyx's, to the pod directly.
`terminationGracePeriodSeconds: 120` (§A.1); every
container's requests equal to its limits, from values (§A.3); and the probes: for Sindri a startup probe (generous, for the first
volume setup), a readiness and a liveness probe, **all three `exec` probes** that run `curl -fsS --max-time 4 http://127.0.0.1:<port>/sindri/ping` inside Sindri's container (`curl` is in the image, A.1). Their timings are set, because the kubelet's default `timeoutSeconds` for an exec probe is 1, which fires before curl's own limit while a CPU-limited Sindri is busy: startup `periodSeconds: 10`, `failureThreshold: 60` (ten minutes for the first volume setup), `timeoutSeconds: 5`; readiness `periodSeconds: 10`, `timeoutSeconds: 5`, `failureThreshold: 3`; liveness `periodSeconds: 20`, `timeoutSeconds: 5`, `failureThreshold: 6` (two minutes of failures before a restart, so a throttled Sindri in the middle of an index build is not restarted). Liveness calls only `/sindri/ping`. The probe's curl runs in Sindri's container, inside its own 1 vCPU cgroup, so it competes with index builds and the Temporal child. An `httpGet` probe is impossible here: the kubelet connects to the pod's address,
where nothing listens, and a probe host of `127.0.0.1` would be the node's loopback, not the pod's. For Onyx's containers liveness probes only (§A.3 Start
order); the agent containers have no probes in v1 (a crash-looping agent restarts under the pod's restart policy and gates nothing). The pod carries `podAnnotations`, whose defaults are the mesh
opt-outs `sidecar.istio.io/inject: "false"` and `linkerd.io/inject: disabled`: there is no listener to mesh, but an injected sidecar without equal requests and limits would demote the pod to Burstable, and a proxy would sit between the agents and their model providers; a deployer adds the keys of any other mesh. Logs are JSON lines on stderr
(`AW_LOG_LEVEL`), read with `kubectl logs -c <container>`. Telemetry export goes to `telemetry.endpoint` when set. Sindri's and
Ollama's security contexts are non-root, read-only root, **all capabilities dropped**, no privilege escalation, default seccomp;
Onyx's containers get the strictest context their image allows, all capabilities dropped and only the proven ones added back
(§A.3, recorded per container by K-S0). **Nothing is privileged.** Values hold every deployer-specific thing: registry, namespace,
the git hosts' credentials (one Secret key per host; the repos themselves are added with `sindri-pod.sh repo add`, which writes the
profile, and the hosts `repo-pull` may use are a profile key, §C.2; a changed Secret needs a pod restart),
storage class, resources, `sindri.port` (the API port, default 7410), `onyx.platform`, `onyx.port`, `telemetry.endpoint`, `podAnnotations`, `git.credentials` (below), `agents` (below), `onyx.existingSecret` (A.3 Secrets) and `onyx.enabled` (default `true`; `false` leaves every
Onyx container, the `onyx-data` claim and its Secret out and sets `AW_SINDRI_ONYX_ENABLED=false`, for a pod that serves code and docs only and is smaller).
**The chart's values never set profile keys**: `context.sessions.enabled`, `index.graph.enabled`, `repo-pull.allowedHosts` and the rest live in the
profile only and change with `sindri-pod.sh profile edit` (§C.3); the chart's own switch for the agents is an empty `agents` list and `helm upgrade`. The chart ships a `values.schema.json` (Kubernetes **1.29 or later**, the version the chart is
tested on and the kind run is pinned to), an example values file, and a `helm lint` plus `helm template` test in CI (rendered
against the example, checked for the security contexts of §A.3 and §C.1, for "no `privileged`, no host path, no Docker socket"
anywhere, for "no Service", for the agent rules below, and for "every image is a digest"). The Kubernetes Secret for git is mounted into Sindri's container only.
There is no PodDisruptionBudget, no snapshot CronJob and no NetworkPolicy in v1 (§11).

**The agents (`agents[]`, empty by default).** Each entry is one container of the pod, with its own image and login; a pod with none is the Sindri and Onyx unit without agents. An entry has `name`, `image` (a digest), `command` and `args`, `env`, `resources` (requests equal to limits; default 4 vCPU and 8 GiB, plus an `ephemeral-storage` request and limit of 10 Gi for the container layer, its logs and a 1 Gi `/tmp` `emptyDir`; 2 vCPU and 4 GiB is the floor for docs-only agents), `workspace` (`size`, default 40 Gi, and `persistent`, default true; see Storage below), `credentialSecret` (see Credentials below), `mcpRepos` and `mcpConfig` (B.2), an optional `preStop` command, and `uid` (default 20001 plus the entry's index; Sindri's is different). The agents clone their own repos into their workspace with their own credentials (they don't use `/data/repos`, which is Sindri's), and Sindri's image holds no agent login: K12 holds.

*Storage.* **Each agent's workspace claim is a standalone PersistentVolumeClaim the chart creates** (named `<release>-agent-<name>`), not a `volumeClaimTemplates` entry (a StatefulSet's templates cannot change after creation, so agents could not be added or removed), and it carries **`helm.sh/resource-policy: keep`**, as Onyx's Secret does. The consequences, said plainly (deploy.md repeats them): removing an agent from `agents[]` and running `helm upgrade` leaves its claim, with its clone and login cache, in the namespace; `helm uninstall` leaves all of them; they keep using volume capacity, and the volume formula below keeps counting them, until the owner deletes them: `kubectl get pvc` lists them and `kubectl delete pvc <release>-agent-<name>` removes one (do it only when the agent's work is pushed). Adding the agent back under the same name finds its old claim again (a kept claim keeps Helm's ownership annotations, as the Secret does); `workspace.size` may be raised later where the StorageClass allows expansion, never lowered: a smaller `size` than the kept claim's makes the API server reject the upgrade, and the kind run checks the message names the claim. The claim holds the agent's `HOME` (its git clone, tool caches such as NuGet and npm, the CLI's session transcripts and login cache) **and its `TMPDIR`** (`<workspace>/tmp`, set by the chart), because disk pressure outside the claim is not harmless: a full claim gives that one agent "no space left" errors, but the kubelet evicts the **whole pod** when local ephemeral storage goes over its limits (Guaranteed QoS prevents none of this).

**How Kubernetes counts ephemeral storage, and what the chart bounds.** A container's `ephemeral-storage` limit covers its writable layer and its logs. The contents of an `emptyDir` are charged to the **pod**, not to one container, and the pod is evicted when its layers, logs and `emptyDir`s together pass the **sum** of its containers' limits, when one container passes its own limit, or when one `emptyDir` passes its own `sizeLimit` (the kubelet checks on a periodic sweep, so the eviction is not instant). So the chart bounds every cause: **every `emptyDir` it creates has a `sizeLimit`**, and **every container carries an `ephemeral-storage` request equal to its limit**, so the pod's sum is defined and each owner of a cause is bounded:

| Container | `ephemeral-storage` limit | What it covers |
|---|---|---|
| `sindri` | 2 Gi | layer and logs 1 Gi; its `/tmp` `emptyDir` (`sizeLimit` 1 Gi) |
| `ollama` | 1 Gi | layer and logs (its model weights are on Sindri's claim) |
| Onyx's eight containers | 12 Gi together: `nginx`, `api_server`, `background` and `inference_model_server` 2 Gi each; `web_server`, `relational_db`, `opensearch` and `cache` 1 Gi each | layers and logs; nginx's four `emptyDir`s (`sizeLimit` 128 Mi each), the three log `emptyDir`s (512 Mi each), `background`'s `/tmp` (256 Mi, if K-S0 shows the bot-flag command needs it); Postgres's `/dev/shm` is memory-backed, `sizeLimit` 1 Gi, and counts as memory (K-S0 re-measures all of these) |
| each agent | 10 Gi by default (a value) | layer and logs; its `/tmp` `emptyDir` (`sizeLimit` 1 Gi) |

The pod's ephemeral-storage total is therefore 2 + 1 + 12 = 15 Gi plus 10 Gi per default agent (25 Gi for one, 65 Gi for five). The only writable places outside an agent's claim are small and bounded: its container layer and a `/tmp` `emptyDir` with `sizeLimit: 1Gi`; a tool that ignores `TMPDIR` and fills `/tmp` still evicts the pod, which is why the kind run fills `/tmp` in the test agent (§7) and the cost is stated in the box. A non-persistent workspace (`persistent: false`) is an `emptyDir` whose `sizeLimit` equals `workspace.size`; it is counted against the pod's ephemeral-storage total and bounded by its own `sizeLimit`, so `values.schema.json` requires that agent's ephemeral-storage limit to be at least `size` plus 2 Gi, and the disk formula below counts such an agent by that limit alone (its workspace is inside it, not a volume).

*Credentials.* There is no interactive login in a pod. Each agent's model login and git credential come from **one per-agent Kubernetes Secret, created by the owner and named in that agent's `credentialSecret`**; never Sindri's Secret, never Onyx's (rule 4). Its keys are the agent's: for a Claude Code agent exactly one of a long-lived token in `CLAUDE_CODE_OAUTH_TOKEN` (made once with `claude setup-token`; it needs a Claude subscription) or an API key in `ANTHROPIC_API_KEY` (for a deployer billed by API), never both in one Secret, because the CLI warns about the conflict, and a git credential key (a read token for the clone, and a push token if the agent pushes). **Delivery is environment variables by default** (`credentialSecret.mode: env`): each key becomes an env variable of the same name, which needs no file permissions and matches how Sindri's own pointers work (K9). `mode: file` mounts the Secret read-only at `/etc/agent/secret` with `defaultMode: 0440`, because a non-root agent uid reads a file only through the pod's `fsGroup`, and the default 0400 would leave it unreadable. The agent's entrypoint turns the git key into a credential (a `GIT_ASKPASS` helper or a credential helper that reads the variable, never a token in a URL), clones with it into the workspace and, on a later start, finds the clone and the login cache already there. The workspace holds the clone and the CLI's transcripts and login cache, not the secret itself. The owner creates each agent's Secret before `helm install` (§0, C.3). That a token in `CLAUDE_CODE_OAUTH_TOKEN` is accepted headlessly is the vendor's documented behaviour, not run here: a kind-run check with the real agent image.

*Permission for Sindri's tools.* A headless Claude Code run asks permission for each MCP tool, and nobody answers in a pod: an interactive agent would stall on its first Sindri call, and one run with `-p` would have the call refused. For `mcpConfig.format: claude` the chart therefore puts, beside `--mcp-config=/etc/agent/mcp.json`, the single token `--allowedTools=mcp__sindri-a,mcp__sindri-b` (one `mcp__<entry>` per `mcpRepos` name; Claude Code's pattern that allows every tool of one MCP server) **at the front of the agent's `args`, before the deployer's own args**. **Why one token with `=`, and first:** `--mcp-config` and `--allowedTools` both take a list (`<configs...>`, `<tools...>` in the installed CLI's help, version 2.1.309) and consume every following word that does not start with `--`; written as two words and followed by a prompt or a subcommand word, they would swallow it (the agent would start with no prompt, or fail on a missing file, silently in a pod). Each entry's name is the chart's own (B.2: `sindri-` plus the repo name with anything outside `[a-z0-9_-]` turned into `-`) and the same string is written in the config file and in the flag, so the permission pattern depends on no renaming by the CLI (names of letters, digits, `_` and `-` are not altered; the kind check lists the tools the test agent really sees and calls one with no prompt). The flag spellings and the pattern are that **kind-run check**; only the list behaviour was read in the CLI's help, nothing was run here. It allows Sindri's tools only; every other permission is the deployer's `args`. The agent's `command` receives the chart's flags first, so the example entrypoint passes them on with `"$@"`:

```yaml
agents:
  - name: builder-1
    image: registry.example.com/agent@sha256:…
    command: ["sh", "-c", 'claude --continue "$@" || claude "$@"', "agent"]   # "agent" is $0; "$@" is the chart's two flags, then args
    args: ["-p", "Work the queue for repo-a."]
    mcpRepos: [repo-a]
# the container starts: sh -c '…' agent --mcp-config=/etc/agent/mcp.json --allowedTools=mcp__sindri-repo-a -p "Work the queue for repo-a."
```

`claude --continue` exits with an error when the clone has no earlier conversation (the first start), and `|| claude` then starts fresh; a run that fails for another reason also starts a second, fresh one, which a deployer who minds checks the exit code for.

The chart enforces these rules, and a `helm template` test asserts each (§7):

1. An agent container mounts only its own workspace, its own credential Secret and its own MCP ConfigMap. It never mounts `/data`, a subPath of it or `onyx-data`, and shares no `emptyDir` with Sindri. The pod's `fsGroup` adds its group to every container's processes but gives an agent no access to a volume it does not mount; the kind run checks that one agent cannot list another's workspace.
2. It runs as its own uid, non-root, with a read-only root filesystem, all capabilities dropped, no privilege escalation and the default seccomp profile. The pod sets `automountServiceAccountToken: false` and no `shareProcessNamespace` (a shared PID namespace would let a same-uid process read `/proc/<sindri pid>/environ`).
3. The chart creates no ServiceAccount rights at all, so nothing in an agent container can `exec` or `attach` into Sindri's container; deploy.md says the same of whoever runs the agents' tooling.
4. No agent gets Onyx's Secret or a Secret that Sindri's `env:` pointers use, by `env`, `envFrom` or volume, and the agent image does not set `AW_SINDRI_HOME` or `AW_STATE_DIR` (an agent that ships the `sindri` CLI looks for a home of its own, finds none and can do nothing with the pod's).
5. The schema's minimums apply to the agents' resources, the image must be a digest (the deployer's own image, so it need not be in our locks), and every entry's `name` is unique and a valid container name.

**What a pod restart does to an agent.** A restart (a Sindri upgrade, a node drain, any `helm upgrade`) sends every container the stop signal at once (A.1). **What survives:** the agent's workspace claim, so its clone, uncommitted files, tool caches, login cache, session transcripts and `TMPDIR`. **What does not:** running processes (the CLI's live session, builds, tests, dev servers), anything in an `emptyDir` (the small `/tmp`), and any Sindri call in flight (a `sindri_request` that had returned its receipt is safe in the ledger; one that had not is simply not filed, and the agent files it again). **How the agent resumes is its entrypoint's job:** its `command` must start from workspace state (for a Claude Code agent, `claude --continue || claude`, the example above: `--continue` re-opens the last conversation in the clone and exits with an error when there is none, the first start, and `|| claude` then starts fresh); the chart's responsibility ends at restarting the container with the same claim, Secret and config. The pod's 120 s grace period is shared by all containers, so an agent that wants to checkpoint handles SIGTERM or sets `agents[].preStop`. **Before an upgrade the owner quiesces** (a deploy.md step, C.5): ask each agent to commit or push work in progress, optionally decide the waiting requests first (they survive the restart in the ledger and are not lost; an agent whose process stops cannot act on the answer until it resumes), and run `helm upgrade` in a quiet hour.

**Why 4 vCPU, 8 GiB and 40 GiB per agent:** a coding agent runs its CLI (about 0.5 to 1 GiB), usually a language server (1 to 2 GiB for Roslyn, 0.5 to 1 GiB for tsserver) and the build and tests of a repo; a .NET solution build alone peaks at 2 to 4 GiB, and this repo's own notes record about 3.5 GB for a full-solution `dotnet format`. With requests equal to limits, an agent over its memory limit has its build killed, so 4 GiB is too tight for this workload. For disk, a NuGet cache of several GB (3.3 GB seen here), `obj` and `bin`, `node_modules`, a git worktree per task and browser caches fill 20 GiB quickly. 4 vCPU because a CPU-limited build looks like a hang, and 2 vCPU shared by the CLI, a language server and a parallel `dotnet test` is slow enough to trip agent timeouts. 2 vCPU, 4 GiB and 20 GiB stays the schema's minimum, for docs-only or light agents. These are a stated default from those figures, not measured here; the kind run with a real agent image records the real use, and each agent's size is a value. **The price of the single-pod layout:** the pod must be Guaranteed (requests equal to limits on every container), so no agent can burst above its share: a build that needs more is throttled at its CPU limit or has its process killed alone at its memory limit, and neither starves Sindri or Onyx. **Disk is different:** when a container exceeds its `ephemeral-storage` limit, an `emptyDir` its `sizeLimit`, or the pod's total the sum of its containers' limits, the kubelet evicts the whole pod, Sindri and Onyx with it, and Guaranteed QoS does not prevent that. That is why an agent's bulk writes (clone, caches, `TMPDIR`) sit on its own workspace claim, where a full claim hurts that agent alone, and why only a small `/tmp` and the container layer, bounded by the limits of the table in Storage above, count against the pod. Burst headroom would mean a Burstable pod, and an eviction could then take Sindri down with it; this spec does not choose that.

**Starting requests = limits** (the schema minimums; each is a value the deployer may raise): `sindri` 1 vCPU and 4 GiB, `ollama` 1 vCPU and 3 GiB, Onyx's containers 5 vCPU and 18 GiB together, split by container in K-O1's render (`opensearch` 2 GiB heap in a 4 GiB limit, `relational_db` 2 GiB plus its 1 GiB memory-backed `/dev/shm`, `inference_model_server` 4 GiB, `api_server` 2 GiB, `background` 3 GiB, `web_server` 1 GiB, `cache` 512 MiB, `nginx` 256 MiB: 17.75 GiB). That is 7 vCPU and 25 GiB (and 15 Gi of ephemeral storage, C.1 Storage) before the agents. **Guaranteed QoS needs requests equal to limits on every container, init containers included:** the chart sets them on all, and its mesh opt-outs keep an injected sidecar without them from demoting the pod to Burstable; deploy.md says so. These are a starting point from the published figures, not measured here. K-A1's `docker run` measures Sindri and Ollama, K-S0 and the kind run measure the pod, and the numbers may move in a later revision of the chart; the floor above is what the owner provisions.

**The costs of this layout, once more, for deploy.md's first section:** every Sindri upgrade or pod restart (a changed value, a node drain) restarts all the agents; **and every change to `agents[]` or `mcpRepos` (a new agent image digest, one more repo, an agent removed) is a `helm upgrade` of the whole pod, so it restarts Sindri and Onyx too: one agent's image bump interrupts everyone, and Onyx answers degraded for minutes while OpenSearch starts cold**; one node is one failure domain; Sindri stays a single copy; and a new repo the agents should reach is such a values change, unless the repo was listed in `mcpRepos` before it was approved (so list every expected repo up front). **The first lever on the agents is `context.sessions.enabled: false` in the profile**, which needs no restart but stops the map tools only: agents can still read the queue and file requests, and a filed request does nothing until the owner decides it. **To cut them off entirely, scale them out (`agents[]` change): that restarts the whole pod.** An agent that fills the scratch space outside its claim evicts the pod (see the price above).

**From a Secret key to the credential pointer.** A git credential is a Secret key that becomes one environment variable in
Sindri's container only, and the profile points at the variable with `env:NAME`. The values file maps one to the other:

```yaml
git:
  credentials:
    - host: git.example.com        # must also be in the profile's repo-pull.allowedHosts
      secret: sindri-git           # an existing Secret in the namespace
      key: token                   # its key
      env: GIT_TOKEN_EXAMPLE       # the variable it becomes in Sindri's container
```

and the repo is then added with `scripts/sindri-pod.sh repo add repo https://git.example.com/team/repo.git --credential env:GIT_TOKEN_EXAMPLE`.
The chart test checks that every `env:` pointer in the example profile names an `env` of the example values. A changed Secret
needs a pod restart.

| The pod shows | What it means | What to do |

| `ImagePullBackOff` | the registry, a digest, or `onyx.platform` doesn't match the nodes | `kubectl describe pod` names the image; check the platform value |
| `CrashLoopBackOff` on `sindri` | Sindri is down, so the agents have nothing to ask | `kubectl logs -c sindri` |
| `CrashLoopBackOff` on an Onyx container (say `opensearch`) | **Onyx is down and Sindri is up**: the agents still get code and docs, and the records linked from Onyx come back with its degraded note. The pod reads not Ready, but Sindri still answers | `kubectl logs -c opensearch`; `doctor` names the container whose port doesn't answer |
| `CrashLoopBackOff` on an agent container | that agent is down; Sindri, Onyx and the other agents carry on | `kubectl logs -c <agent>` |
| `Running` and Ready, but Onyx misbehaves | Onyx containers have no readiness probes, so Ready says nothing about Onyx | `sindri doctor` (its Onyx rows) |
| `OOMKilled` | a container's memory limit is too small | raise that limit and `helm upgrade`: the pod rolls although it is not Ready (`podManagementPolicy: Parallel`, A.3); if it does not, `kubectl delete pod <pod>` (a normal delete, never forced) recreates it from the new template (the schema's minimum is the floor) |
| `Evicted` | node pressure, **or a container exceeded its `ephemeral-storage` limit, an `emptyDir` its `sizeLimit`, or the pod's total passed the sum of its containers' limits; each evicts the whole pod** (`kubectl describe pod` names the reason) | for node pressure, a bigger node (the pod is Guaranteed QoS, so it is the last to go); for an agent, find the tool that ignored `TMPDIR`, point it at the workspace, and raise that container's limit if its layer or logs are the cause |

Onyx needs no values file of its own beyond `onyx.*` above: the script renders its containers from its pinned Compose file. Its
admin sign-up page is on the pod's loopback only, so no other pod in the cluster can reach it; inside the pod, Sindri, Ollama,
Onyx's other containers and the agents could, so the owner makes the admin account soon after install, with `connect --onyx` (§C.3), before
connecting any source (until it runs, Onyx's first account is unclaimed, and the NOTES say so), and `attach` refuses an account it did not expect (B.3). The kind run records the whole footprint (CPU,
memory, disk of every container) in `docs/sindri/deploy.md` so the owner can size the real cluster's node.

### C.2 The repo service (engine lane)

`repo-pull` (a Sindri service, on by default in pod mode and opt-in elsewhere like `context-docs-refresh`, every 1 minute; at most one refresh per repo in flight, moves of main while one runs are coalesced into one follow-up, and the index, map and docs refresh keep a minimum interval of 5 minutes per repo, so a busy main doesn't queue endless rebuilds on the one writer):
- for each profile repo with a `pull:` block (`{ url, credential: env:NAME }`): the first time (and again whenever the directory is missing: the service clones when `/data/repos/<name>` is absent, so deleting it is the fix for a repo that cannot be updated, `SND-REPO-002` and `-003`), `git clone --no-hardlinks` into
  `/data/repos/<name>` (the profile's `path` must be under `AW_SINDRI_REPOS_DIR` in pod mode); after that `git fetch origin
  <default branch>` and `git merge --ff-only`; a dirty tree or a non-fast-forward is a doctor row and a needs-you row, never a
  reset; the credential is passed through `GIT_ASKPASS` reading the pointer, never in a URL or an argument, and the helper answers only for the host of that repo's URL; the repo `<name>` must match `[a-z0-9][a-z0-9._-]*` and resolve under `AW_SINDRI_REPOS_DIR`; the URL must be https (v1; an ssh key would need a secret and a `known_hosts` file, a later addition) and its host in the profile's `repo-pull.allowedHosts` (profile-only: changing it is a profile change the owner approves, not a chart value), `--` precedes it on every git call, and git runs with `protocol.file.allow=never`, `http.followRedirects=false`, hooks off (`core.hooksPath=/dev/null`) and submodules off; the credential should be read-only (doctor can't check that; deploy.md says so);
- `code-index-main-move` then sees HEAD move and indexes, and the map and docs refresh follow, as on a laptop. The freshness number is the map's lag behind main, shown in doctor and as `lagSeconds` in the `stale` note an agent sees, and exported as a metric (telemetry export is on in pod mode, off by default elsewhere); a lag over 15 minutes is a doctor warning.

v1 pulls and indexes each repo's default branch only: an agent working on a feature branch gets main's map, which deploy.md says.

`sindri repo add` in pod mode takes `--url`, `--name` and the credential pointer instead of an existing path, and writes the `pull:` block to the profile file; it clones nothing. **`repo-pull` reads the approved profile only** (the repos, their `pull:` blocks and `repo-pull.allowedHosts`), so a repo that `repo add` recorded is cloned after the approval, not when it is added; `repo add` itself, an owner action, checks the host against the live file so the owner can add before approving.

### C.4 Network rules and who can read what

There is no NetworkPolicy on the namespace by default, and the chart ships none in v1 (a reversible default, §11), and none is needed for ingress: Sindri's API, Temporal,
Ollama and every Onyx container listen on the pod's loopback only, and nothing listens on the pod's address, so no pod outside this one
can connect to anything in it (§6). The owner's routes are reachable only from inside the pod and
through `kubectl port-forward` and `exec`; the listener settings of §A.3 and the loopback listener of §B.2 keep them the owner's. `kubectl exec` and `port-forward` rights are the owner's power
(they reach the human token, the ledger and Onyx's admin page), and so are volume-snapshot read rights and the right to create a
pod or claim in the namespace (they reach the human token, the ledger, Onyx's database with the connector OAuth credentials, and
Sindri's Onyx token). **The namespace is the owner's alone**; deploy.md says so in its first section, next to the costs of the layout (C.1), and says to use an encrypted StorageClass where the cluster has one. A deployer who wants egress rules lists the git
and forge hosts, Onyx's registries and connector services, the model hub (§A.3) and each agent's model provider. A NetworkPolicy works per pod, not per container, so these rules bind Sindri, Onyx and the agents alike; the agents' egress is the thing a deployer will most want to restrict, and the rule list has to include what Sindri and Onyx need as well.

### C.5 Upgrading and getting back

`docs/sindri/deploy.md` gains: upgrading Sindri (a new image digest in the values, `helm upgrade`, the pod restarts and takes the
lease; Onyx's containers restart with the pod, so Onyx answers degraded for a few minutes; the only downgrade is the previous
digest plus, if state moved, a snapshot restore), upgrading Onyx (**bump the pin in `context/onyx.lock`, `onyx-lock.sh verify`,
refresh `deploy/onyx/docker-compose.yml`, run `node scripts/onyx-pod.mjs`, read the diff, build a new Sindri image that embeds
the new lock, `helm upgrade`, then `sindri onyx attach` again so the profile's pinned version follows**; doctor's `/api/version`
row shows a mismatch until it does; Onyx's database migrations run forward at `api_server` start, so the only way back is a
snapshot restore), and the manual backup and restore of K7 (snapshot both claims at the same moment, restore both from the same pair, so the map's Onyx cursor and Onyx's database match; the heavy test runs this restore once). The procedure includes exporting Onyx's Secret with the snapshots (K7) and restoring it first; the heavy test restores into a fresh namespace with the exported Secret. Changing `agents[]` or `mcpRepos` (an agent's image digest, a repo, an agent removed) is also a `helm upgrade` of the whole pod: Sindri and Onyx restart with the agents and Onyx answers degraded for a few minutes, so batch agent changes into one upgrade. **Before an upgrade (quiesce):** ask each agent to commit or push its work in progress, optionally decide the waiting requests first (`sindri decisions --pending`; they survive the restart, but an agent whose process stops cannot act on the answer until it resumes), and run `helm upgrade` in a quiet hour; running processes stop at the restart, files on the workspace claims stay (C.1). **Agent claims outlive the agents:** removing an agent from `agents[]` or running `helm uninstall` leaves each workspace claim (`helm.sh/resource-policy: keep`); list them with `kubectl get pvc` and delete one with `kubectl delete pvc <release>-agent-<name>` once its work is pushed; until then the disk is still in use.

deploy.md also has **"Starting Onyx over"**, the fix text of `SND-ONYX-014` when you did not make the account, with a warning that it deletes everything Onyx holds (its data, its accounts, its connectors and their OAuth credentials): `helm uninstall <release>` (this removes the pod; the claims and Onyx's kept Secret stay), `kubectl delete pvc <the onyx-data claim>` (`kubectl get pvc` names it), and, only if you also want fresh passwords, `kubectl delete secret <Onyx's Secret>`; then `helm install` again and `connect --onyx` for the new first account.

## 6. Security

- **Local callers only.** Sindri's API is a loopback listener, as on a laptop, and nothing listens on the pod's address, so nobody
  outside the pod can reach it. The callers are the containers of the pod: the owner's forward and `exec`, and the agents. Every
  one that is not the human is a repo-scoped, fenced session, **not authenticated against its neighbours** (K5). The protected verbs
  need the per-start human token, which lives in Sindri's volume (`auth/`, owner-only) and which the agent containers cannot read
  (the container rules below); an agent that sends `X-Sindri-Caller: human` without it gets 403 `SND-AUTH-001`, and `/sindri/mcp` strips the header.
- **What an agent can read** (K4, K5): the maps of the approved repos (labels, kinds, edges, the tools' cited code and docs snippets,
  which already pass the egress scrub), the chat and ticket records already linked into those maps (the owner's rule of 2026-10-15;
  an agent never queries Onyx), and the items, queue and pending decisions of a repo it names. Any process in the pod can name any
  approved repo, so every agent is trusted with every approved repo; that is accepted under the honest-mistake model.
- **Nothing is privileged**, there is no Docker daemon or socket, and no pod host path. The cost of dropping Docker's private
  network: **the pod's loopback is shared by every container in it**, so the boundary inside the pod is the pod. Ollama, every
  Onyx container (api_server, background workers, the model servers, the web server, Postgres, OpenSearch, Redis, nginx) **and every agent** can reach
  Sindri's API on `127.0.0.1` with no token, as a session: the 13 tools (`sindri_request` among them) and the session-level API,
  though a human-only action (approvals, protected verbs) still needs the per-start human token they
  cannot read; the Temporal dev server's unauthenticated frontend (a session-level caller there could signal or cancel a workflow);
  Redis, which Onyx's Compose file leaves without a password; and Onyx's web, API and nginx (including its first sign-up). Onyx's
  Postgres and OpenSearch need their passwords, which are in Onyx's Secret, and **no agent container gets that Secret** (nor Sindri's `env:` pointer Secrets). The sharpest
  case remains Onyx's connectors (`background`) and web connector, which fetch addresses the owner gives and whose results Onyx stores: a
  connector pointed at `http://127.0.0.1:7410/…` would read Sindri's own API as a session. **Accepted for v1** under the
  honest-mistake model (pinned prebuilt images, connectors chosen by the owner, agents the owner runs); mitigations: the connector checklist says to give
  the web connector only public URLs (and warns against `localhost`, `127.0.0.0/8`, `::1`, the pod's address and `*.svc`), Temporal runs headless in pod mode (no UI port), K-S0 records whether Onyx's own web-connector guard already blocks loopback, including through a redirect to loopback and through a DNS name that resolves to `127.0.0.1`, a later spec could put Sindri's API behind a Unix socket or a token for sessions (K-I1) and Temporal's frontend behind one too, and the agent rules below keep the rest closed. The alternative, noted: Onyx
  in its own pod, which `OnyxSettings.CheckUrl`'s loopback rule forbids today.
- **The agent containers' rules** (C.1, tested in §7). Without them an agent would hold the owner's rights, because over raw HTTP the human token is the whole gate: an agent container never mounts Sindri's data volume (`/data`, which holds `auth/human.token`, the ledger and the Onyx token), runs as a different uid, has no service-account token and no RBAC (so no `exec` into Sindri's container), and the pod does not share its process namespace (`/proc/<sindri pid>/environ` and its file descriptors stay unreadable). Nobody gets a terminal into the Sindri container through the agents. The agents bring their own login and git credentials in their own Secret, mounted into that container only.
- **What listens on the pod's address**: nothing. Every Onyx container, Temporal
  (`--ip 127.0.0.1`), Ollama (`OLLAMA_HOST`), Sindri's API and the agents' own tools are loopback-only or silent. An agent that starts a dev server on
  `0.0.0.0` would publish it on the pod's address; deploy.md and the chart's NOTES say to bind agents' servers to loopback, and the kind run scans the pod's address with the test agent running (§7). Whether each Onyx image honours its loopback setting is **unverified until K-S0**, which reads the pod's listeners once (A.3) and
  scans the pod's address from another namespace, and must find nothing.
- **Secrets** live in Kubernetes Secrets and reach Sindri as `env:` pointers; the image and the chart's values hold none; Onyx's
  secrets are a chart-made Secret mounted into Onyx's containers only; each agent's credentials are its own Secret in its own container; the Onyx token Sindri makes stays on the encrypted volume,
  owner-only.
- **Onyx's first account is unclaimed until `connect --onyx` has run.** Any container of the pod, an agent among them, could register first. `attach` refuses an account it did not expect (`SND-ONYX-014`), and the chart's NOTES say that the step should follow soon after install, once doctor shows Onyx ready. **After that first account, Onyx must refuse new sign-ups** (K-S0 item 6, required): otherwise an agent could register a second account from the pod's loopback and read Onyx directly, contradicting the rule that agents never query it (q82). If v4.9.0 cannot close sign-up, this is named plainly here and in the NOTES, and the owner decides.
- **Onyx's Secret outlives an uninstall** (`helm.sh/resource-policy: keep`) and is part of the backup (K7), because it holds the key to the stored connector credentials; `onyx.existingSecret` lets the owner supply it (A.3 Secrets).
- **Snapshots and claims are the secrets store.** Anyone who can create a pod or a claim in the namespace, or read a volume
  snapshot, reads the human token, the ledger, Onyx's database (the connector OAuth credentials), Sindri's Onyx token and the agents' workspaces (their clones and logins). The
  namespace is the owner's alone, snapshots are a manual procedure the owner runs, and the StorageClass should be encrypted
  where the cluster has one (§C.4).
- **Supply chain.** Every kubelet image by digest: our own, the base images and Ollama in `deploy/images.lock`, Onyx's in
  `context/onyx.lock`, the agents' in the deployer's values; our own image built from the repo by CI, both locks checked in CI, and the rendered Onyx template checked
  against them by `onyx-pod.mjs --check`; a `helm template` test asserts every image in the chart is a digest (and ours and Onyx's are from a lock). Model
  weights are pinned too (Hugging Face revisions, Ollama's digest) and verified before Sindri serves queries.
