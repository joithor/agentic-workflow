How Sindri Works
01

Why Sindri exists

You assign yourself a ticket. Here's everything that should happen next without you.

Start with something you already do

Picture your Monday. You open the tracker, assign yourself a ticket, paste it into an agent session, and then spend the afternoon steering. "No, not that file." "You forgot the migration." "Did you actually run the tests?"

Sindri is a local, always-on harness that takes over that afternoon. It picks up the work, sizes it, starts agent sessions with cited context, keeps them on track and ships them through a fixed recipe. It asks you only when it has to.

⚒️
The name

Sindri is the dwarf smith who forged Draupnir, a ring that makes copies of itself. The core tenet is the same idea: the human approves direction; Sindri does the finding, the building and the proving. Then it uses that factory to improve itself.

The night watch

A short tick, a single writer, bounded work, and the cheapest rung first.

A watchman doing rounds

A night watchman doesn't sit in one room waiting for trouble. Every few minutes they walk the building, check each door, write in the logbook and move on. That's the tick.

Only one watchman holds the key

Two ticks running at once would double-start sessions. So the first thing a tick does is take a lock, using a trick the filesystem guarantees: renaming a folder onto a name that already exists fails. built

sindri/src/lock/lock.ts 
    for (let attempt = 0; attempt < 3; attempt++) {
      // Atomic: rename fails while sindri.lock exists (it is never empty).
      if (tryRename(tmp, lockPath)) return won(o, lockPath, me);
      const holder = readOwner(lockPath);
      const age = ageMs(lockPath, o.now);
      if (age === null) continue; // released in between: try again
      if (!provablyDead(holder, age, o.sys)) return { ok: false, heldBy: holder, detail: describe(holder) };
PLAIN ENGLISH

Try up to three times.

Renaming can't half-succeed, so two ticks can't both win.

If our folder became sindri.lock, we hold the key.

Otherwise, who holds it?

And how old is their lock?

If it vanished while we looked, just try again.

Unless the holder is provably dead (wrong process, rebooted host), back off and report who has it.

A stale lock can be taken over, which raises a risk: the old holder wakes up and writes anyway. So every write carries an epoch, and the ledger refuses old ones (fenced() in ledger/db.ts, error SND-LOCK-003).

Survey before you dig

Find every surface a project touches before the code does, and prove it on old projects.

Call before you dig

Before a crew digs, a surveyor marks every buried pipe and cable with paint. Hitting one mid-dig is how a two-day job becomes a two-week one. Projects sprawl the same way, when the surfaces and implications are found during implementation.

No paint mark without a source

The model drafts the map, but code checks it. A surface that cites nothing, or cites something that isn't a real source, is rejected:

sindri/src/scope/map.ts 
  for (const s of map.surfaces) {
    if (seen.has(s.id)) reasons.push(`duplicate surface id ${s.id}`);
    seen.add(s.id);
    if (s.citations.length === 0) reasons.push(`surface ${s.id} cites no source`);
    for (const c of s.citations) if (!known.has(c)) reasons.push(`surface ${s.id} cites ${c}, which is not a source reference`);
    if (!inStream.has(s.id)) reasons.push(`surface ${s.id} is in no workstream`);
PLAIN ENGLISH

Walk every surface the model proposed.

The same id twice? Write down why that's wrong.

Remember we've seen this one.

No citation at all: rejected.

A citation the model invented (not a real source): rejected. This is how hallucinated references get caught.

A surface no workstream owns would fall through the cracks: rejected.

The full check also refuses dependency cycles and workstreams without acceptance checks. Then a different model runs an adversarial "what's missing?" pass until nothing new appears.

Where the human decides

Locked doors instead of signs, the right screen for each call, and verdicts that admit what they didn't prove.

A sign versus a locked door

"Staff only" on a door stops polite visitors. A lock stops everyone. Sindri uses both, and never confuses them: hooks force patterns on a cooperative agent; the sandbox enforces security against a hostile one. A hook that fails open costs a missed nudge, never a breach. §5.3, §17.19 C3–C5

writesSign: a pre-tool path guard. Lock: Sindri's verifier refuses any bundle with out-of-scope paths.
commandsSign: a gate on command strings (easily evaded). Lock: missing credentials and network make the command fail anyway.
networkLock only: a per-task egress proxy allowlist.
readsLock: mounts. Only the repo, pack and allowed refs exist in the container.
holdoutsLock: mounted only into evaluator Steps, with a canary example to detect leaks.
⛔
Always denied in sessions (v1)

Undraft, merge, close or cancel items, create items, chat posts, gh api writes, workflow triggers, production-mutating MCP tools, kubectl or exec tools. A denied call parks the item with a typed reason; the session never sits on a permission prompt. §8.1

Nothing secret gets written down

No secrets in packs, ledger, logs, notifications or the eval corpus (invariant 8). Everything passes through the scrubber first, which replaces each secret with a [REDACTED:kind] placeholder. built

sindri/src/scrub/scrub.ts 
export function makeScrubber(extra: readonly ScrubPattern[] = []): Scrubber {
  const patterns = [...BUILTIN_PATTERNS, ...extra].map((p, order) => ({ ...p, re: withFlags(p.re), order }));
  // Only a placeholder naming one of this scrubber's kinds is skipped, so a crafted
  // "[REDACTED:<secret>]" is still scanned.
  const kinds = [...new Set(patterns.map((p) => p.kind))].map(escapeRe).join("|");
  const PLACEHOLDER = new RegExp(`\\[REDACTED:(?:${kinds})\\]`, "g");
PLAIN ENGLISH

Build a scrubber from the built-in secret patterns plus any extras.

Compile each regex and remember its order.

The clever part: scrubbing twice shouldn't double-redact, so existing placeholders are skipped…

…but only real ones. An attacker can't hide a key by writing [REDACTED:sk-live-…] around it.

List the exact kinds this scrubber knows.

A placeholder counts only if it names one of those kinds.

Two jars: stable and next

The harness always runs from a pinned stable install of itself. Changes land on next, are evaluated by stable, soak, then promote. A change may never modify the eval suite that judges it (invariant 11). Here's the gate:

sindri/src/evolve/channel.ts 
  if (c.next === null) return { ok: false, why: "nothing is installed on next", next: "scripts/install-sindri.sh --channel next --ref <sha>" };
  if (c.next.sha !== sha) return { ok: false, why: `${sha} is not what next runs (${c.next.sha})`, next: `sindri channel promote ${c.next.sha}` };
  if (c.stable !== null && c.stable.sha === sha) return { ok: false, why: `${sha} is already stable`, next: "sindri channel status" };
  const days = Math.floor((now.getTime() - Date.parse(c.next.installedAt)) / 86_400_000);
  if (!Number.isFinite(days)) return { ok: false, why: `next has no readable install time (${JSON.stringify(c.next.installedAt)}), so its soak can't be checked`, next: "scripts/install-sindri.sh --channel next --ref <sha>" };
  if (days < SOAK_DAYS) return { ok: false, why: `next has soaked ${days} of ${SOAK_DAYS} days`, next: "sindri channel status (after the soak)" };
PLAIN ENGLISH

Nothing on next? Nothing to promote. Here's the command to install it.

You can only promote exactly what next is running, never some other commit.

Already stable? Nothing to do.

How many whole days has next been running?

If the install time is unreadable, refuse. An unknown soak is not a passed soak.

Not soaked long enough (SOAK_DAYS is 3)? Wait.

Every refusal says why and gives the exact next command to run. The function's last check needs a passing package:sindri suite run at that sha.
