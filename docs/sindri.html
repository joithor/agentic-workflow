    Chapter 1 · Overview

    Sindri grows Sindri.

    Sindri is a local, always-on harness that picks up work, sizes it, starts agent sessions with cited context, keeps them on track and ships them through a fixed recipe. It asks the human only when it has to. Named after the dwarf smith who forged Draupnir, the ring that multiplies itself.

    The human approves direction. Sindri does the finding, the building and the proving. §17 core tenet

    Part of the finding is looking outward. Sindri {{field harvest|harvests other software factories}}: it reads their designs, checks each practice against its own spec, and builds the ones it lacks through its own factory. See chapter 22. §17.25

    It started from a measurement. A transcript audit of one month of work (406 sessions, 2,911 human turns) found that the human's effort went mostly to the least judgment-heavy parts of agent work. §1

    The shape of the whole thing

    Plans 1–5 built the control room: measurement, the {{ledger}}, the code index, the scoping harness and offline self-evolution. Plan 6 (the dashboard) is specced. The factory addendum (§17) designs the production line: from a {{scope map}} through a desk design studio to a frozen {{packet}}, then a factory build of narrow sessions run by {{lens|lenses}}, reviewed from anywhere, and merged by the human. Agent readiness and a C# port come first, so agents can build on a repo that checks what they do.

    Every feature on these pages carries a status: ● built shipped in Plans 1–5, ◐ specced has an approved spec and plan, ○ designed in a design spec but not planned, ✧ dream vision, scouting seeds or deferred. Use the filter above to hide any of them. Underlined terms open a definition.

    Chapter 2 · Rules that never bend

    Nineteen invariants, three principles

    The main spec fixes eleven invariants; the factory addendum adds eight. Three architectural principles follow from the core tenet: Sindri can only evolve parts it can isolate, measure and swap, and it can only afford to run them if most decisions cost no model turn.

    Principle 1

    Modularity

    Every part is a module with a typed contract, an eval suite, telemetry and a registry entry. A part that can't be swapped alone is a design defect.

    Principle 2

    Context management

    No session gathers its own context. Code assembles a budgeted, cited {{injection plan}}. Modules declare what they need; they never load everything that might help.

    Principle 3

    The decision ladder

    Each decision takes the cheapest {{rung}} that can make it with enough confidence: code, a decision model, a small model, then an agent turn. See chapter 5.

    Chapter 3 · The production line

    Scope → studio → packet → workflow → build → review → merge

    The target pipeline from §17.0. Product and design turns happen at the desk, where they belong. Everything after the frozen packet runs without the human until review.

    Chapter 4 · Architecture

    A short tick, a single writer, bounded work

    launchd fires a short deterministic {{tick}}. It never waits on a model: model work runs in bounded jobs and sessions that end, and the tick reads their results from the {{ledger}} on the next pass. §5

    The Step contract §6

    Every unit of work is a {{Step}}: inputs, an output schema, deterministic checks, a verifier, max rounds, a budget and an escalation. The producer never verifies itself.

    Chapter 5 · Cheapest rung first

    The decision ladder

    Each decision takes the cheapest {{rung}} that can make it with enough confidence. It climbs only when the lower rung is below its threshold, and self-evolution keeps pushing decisions back down. §17 principle 3

    Every decision records which rung made it, its cost and its later outcome. "Agent turns that a cheaper rung could have made" is a tracked metric, and the share of decisions made at rungs 1–2 should rise month over month. §17.2

    Chapter 7 · Front of the line

    Find the surfaces before the code does

    Projects sprawl when surfaces and implications are found during implementation. sindri scope turns a brief into a cited {{scope map}} up front, and --backtest proves it on a project's original brief. §7.5

    Scope map contains

    • Surfaces (UI, API, job, data, integration), each with a citation
    • Implications: migration, permissions, reporting, notifications, mobile, flags
    • Workstreams with dependencies
    • Acceptance checks per workstream
    • Open product questions, batched

    Verification loop

    1. Deterministic: every surface cites a source; acyclic dependencies; every surface in a workstream
    2. Adversarial missing-surface pass on a different model, until nothing new appears
    3. Scoping {{direction check}} (from rollout step 5)

    Chapter 8 · Freeze, then compile

    No build without a frozen packet

    The design studio turns a scope map into a {{packet}}: a schema-validated directory frozen by hash. For each Step, a {{task compiler}} (code, no model) computes a {{session spec}}, and the {{sandbox policy}} is compiled from it. Agents don't decide their own scope. §17.4, §17.5, invariants 13–14

    The capability ceiling §17.19 C1–C2

    Every registered artifact is split in two. Prompt text (instructions, questions, rubrics, rule wording) may self-adopt. Capability fields (tool, command, MCP, network, write-scope and budget allowlists; trust tiers; workflow templates; security rules) are always approval-tier, and no model output may set them.

    session policy = profile allowlist ∩ lens allowlist ∩ task spec

    Chapter 10 · A growing library

    Taste, written down and selectively injected

    "I always want X", said once at the desk, becomes a {{rule}}. Rules are registered artifacts with selectors, so a session carries only the few that apply to its repo, paths, task kind, lens and stage. §17.6

    Layers (later wins on the same id)

    Enforcement ladder

    1. Injected text
    2. A judge rule-check in the verifier
    3. A deterministic check at commit and in the verifier

    Chapter 11 · Proof, not claims

    Every acceptance example needs an artifact

    The {{ship contract}} is shared by every worker and by Sindri's ship Step: at most three review rounds, an evidence plan that must be satisfied, and one set of publish rules. {{evidence kind|Evidence kinds}} are pluggable providers, run at base and head, verified by script first. §17.11

    interface EvidenceProvider {
  kind: string;
  applies(task: SessionSpec, changed: ChangedFiles): boolean;
  plan(task): Promise<Result<EvidencePlanItem[]>>;
  run(item, at: "base" | "head"): Promise<Result<EvidenceArtifact>>;
  verify(base, head): Promise<Result<Verdict>>;   // script first, judge only to explain
  publish(a): Promise<Result<PublishedRef>>;     // ask-first rules stay per provider
}

    Chapter 12 · Watch it flow

    One task, from frozen packet to merged epic

    Each packet gets an {{epic}} branch. Task PRs stack against it in dependency order and merge into the epic under a deterministic gate. The epic → default-branch PR is always the human's. Step through it. §17.10

    Chapter 13 · Work that isn't a packet

    Standing workflows fire on events

    A {{standing workflow}} is a workflow template fired by events, using the same lenses, sandbox policies, budgets and handoffs. Each has an {{autonomy tier}}, and moves up a tier only through an approval-tier profile change after its report output reaches a measured precision bar. §17.9

    Chapter 14 · More at once

    From one host to a team, in four rungs

    Today: one active host, a session cap, one heavy job at a time. Inside a packet, tasks with non-overlapping write scopes can already run in parallel. The ladder below adds scale without a rewrite, and each level reuses the one below. §17.20

    Limits that don't go away with more machines

    Model quota

    The capacity router spreads Steps across allowed accounts, never across the work/personal line.

    Human review

    The {{human-minutes}} budget caps how much work Sindri starts, however many workers exist.

    Merge contention

    Conflict-aware dispatch and small write scopes; a task that conflicts twice is serialized.

    Chapter 15 · Serving several people

    From one human to a team

    Scaling across machines (the previous chapter) isn't the same as serving several people. The design so far assumes one human, one SQLite writer, file logs and polling. These are the foundations team mode needs, built in a fixed order so the cheap seams land during the C# port. §17.21

    Chapter 16 · The ring that multiplies

    Improve what exists; find what doesn't

    Everything that shapes agent behaviour is a registered artifact with an eval suite. Proposals come from steering, reflection and overturn patterns; they win a blinded offline comparison before they're adopted.     Two channels

    The harness always runs from a pinned stable install of itself. Proposed changes land on next, are evaluated by stable, soak, then promote with a typed confirmation. A change may never modify the eval suite that judges it (invariant 11). §7.7

    Chapter 17 · Deny by default

    Hooks force patterns; the sandbox enforces security

    A hook that fails open costs a missed nudge, never a breach. The security boundary is a dedicated session container and user, server-side branch protection, and sindri-side re-verification of what a session pushes. §5.3, §8

    Always denied in sessions §8.1

    No allowlist entry can grant these in v1: undraft, merge, close or cancel items, create items, chat posts, gh api writes, workflow triggers, production-mutating MCP tools, and kubectl or exec tools. A denied call parks the item with a typed reason; the session never sits on a permission prompt.

    Chapter 18 · Where the human decides

    The right surface for each decision

    The host CLI stays the authority. A loopback dashboard shows every agent on the machine; over a tailnet, a phone handles binary, low-context decisions, signed with a passkey. Open questions, freezes and protected approvals stay at the desk. §10, Plan 6, §17.12, §17.19

    Phone decision states §17.19 C8

    Each decision signs (item id, item version, nonce, choice). A changed item or a reused nonce is refused. Every swipe also has visible buttons, and every choice can be undone for 10 seconds.

    pendingdecidingdecided heredecided elsewherestaleoffline (queued)passkey failedrevoked device

    Dashboard states (Plan 6) dashboard §4.3

    Exactly one state per session, always written as text, ranked: approval › input › plan ready › auth › working › background › ready › stuck › interrupted › failed › limited › crashed › ended. One attention colour means only "needs you"; under reduced motion its pulse becomes a static outline.

    Chapter 21 · What ships when

    Plans, readiness, factory, distribution

    Every step ends with a "Turn it on" task: run the switch-on command, record the evidence, and use the piece on the next plan's work. Select any milestone. §13, §13.3, §17.16, §17.20, readiness §10

    The bootstrapping rule §13.3

    • A piece not switched on within one working day of its plan merging becomes a ring-0 work item of its own.
    • No later plan is started by hand if the pieces before it could start it.
    • Every ring-1 switch-on waits until the same piece has run on ring 0 for at least one plan's worth of work, with no open defects.

    Chapter 22 · What the field already knew

    Twenty-five practices from other software factories

    A read of other factories (addyosmani/factory, SuperPlane, loki-mode, chainloop, robi42/factory, planwright, dev-sdd-kit and the Actual AI workshop) found practices Sindri didn't have or had only in part: sixteen on a first pass and nine more on a second. Ideas only; no code is copied. Each source also seeds the scout. §17.23

    Three new invariants §17.1, §17.23

    Invariant 17

    Sessions don't edit the tests that judge them

    Existing tests are read-only unless the frozen packet names the change, and a test change always gets a human read.

    Invariant 18

    Production stops when review is full

    No new Step whose result needs a human decision starts while the {{back-pressure|pending-decision queue}} is at its limit.

    Invariant 19

    Every verdict says what it didn't prove

    An item's outcome lists every planned check that didn't run or couldn't decide. Silence is never a pass.

    Merge-confidence card §17.23.7

    Five dimensions, scored 1 to 5: blast radius and drift from the packet (lower is better), reversibility, security and performance (higher is better). Names and thresholds live in Sindri code; a model supplies only a score and a one-line summary. A critical dimension moves the decision from the phone to the desk.

    Never loosened, whatever the evidence: the human merges to the default branch; existing tests are read-only to sessions; the producer never verifies its own work; protected modules need approval; models never grant capabilities. §17.23.8

    Field harvest: Sindri does this reading itself §17.25

    These two passes were done by hand. From F6 they are Sindri's job: a weekly harvest reads the factories in a {{field registry}}, writes practice cards with file-and-line citations and a licence, and checks each against Sindri's own spec. Two models must agree a practice is missing before you see it. build drafts the spec section, updates this guide, and runs the mechanism through the factory like any other work.
